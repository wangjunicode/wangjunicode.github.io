# 游戏客户端增量构建与缓存加速系统：从构建管线原理到工程实践

> 在一次大型项目重构中，全量构建耗时从42分钟优化到7分钟；在CI流水线中，增量构建从15分钟压缩到4分钟。这不是魔法，而是对Unity构建管线的深度理解与工程化实践的结果。

## 一、为什么构建速度是工程效能的关键瓶颈

在大型游戏项目中，构建时间是团队迭代速度的直接制约因素。

| 项目规模 | 全量构建时间 | 日构建次数 | 年浪费工时 |
|----------|------------|-----------|-----------|
| 小型项目(50场景) | 8-15min | 5-8次 | ~200人天 |
| 中型项目(200场景) | 20-40min | 3-5次 | ~400人天 |
| 大型项目(500+场景) | 45-90min | 2-3次 | ~800人天 |

构建速度不仅影响开发效率，还影响：
- **调试周期**：每次代码修改后的验证等待时间
- **CI/CD吞吐量**：流水线排队与阻塞
- **热修复响应**：紧急Bug修复的上线时效
- **开发体验**：频繁打断心流的负面效应

### 1.1 构建时间的组成

一个典型的Unity构建过程包含以下阶段：

```
┌─────────────────────────────────────────────────┐
│              Unity 构建全流程                      │
├──────────┬──────────┬──────────┬─────────────────┤
│   Domain   │   Asset    │   Build    │    Code        │
│  Reload   │   Import   │   Asset    │    Compile      │
│   (2-5s)  │  (30-70%) │  (15-30%)  │    (5-15%)      │
├──────────┴──────────┴──────────┴─────────────────┤
│              总构建时间 = 100%                      │
└─────────────────────────────────────────────────┘
```

- **Domain Reload**：每次进入Play Mode或构建时的脚本域重载
- **Asset Import**：资源导入与处理（纹理压缩、模型转换等）
- **Build Asset**：将处理后的资源打包为AssetBundle
- **Code Compile**：C#代码编译与IL2CPP转换

增量构建的核心目标：**只处理变更的部分，跳过未变更的部分**。

## 二、Asset Database v2：增量导入的基石

Unity 2019.3 引入的 Asset Database v2（ADB v2）是增量构建的根基。理解它的工作原理是优化构建的第一步。

### 2.1 变更追踪机制

ADB v2 的核心数据结构是 **Asset Database State**，存储在 `Library/SourceAssetDB/` 目录下：

```
Library/
├── SourceAssetDB/
│   ├── artifacts.db       # 资源处理产物元数据
│   ├── source.db          # 源文件哈希与依赖关系
│   └── info.db            # 版本控制信息
├── PackageCache/          # 包缓存
├── metadata/              # 资源元数据缓存
└── artifactCache/         # 处理后资源缓存
```

ADB v2 使用 **内容寻址存储（Content Addressable Storage）** 来管理资源缓存：

```csharp
// ADB v2 的变更检测伪代码
public class AssetDatabaseV2ChangeDetector
{
    // 每个源文件的缓存条目
    struct SourceAssetEntry
    {
        public ulong fileId;           // 文件唯一ID
        public Hash128 contentHash;    // 内容哈希（文件全部内容的SHA-128）
        public Hash128 dependencyHash; // 依赖图哈希（引用的其他文件）
        public List<ulong> imports;    // 导入此文件的importer列表
        public DateTime lastWriteTime; // 最后修改时间
    }

    // 变更检测流程
    public HashSet<string> DetectChanges(string projectRoot)
    {
        var changedAssets = new HashSet<string>();
        
        // Phase 1: 扫描文件系统变更
        foreach (var file in ScanFileSystem(projectRoot))
        {
            var cachedEntry = LoadFromCache(file.guid);
            
            // 快速跳过：LastWriteTime未变化
            if (cachedEntry.lastWriteTime == file.lastWriteTime)
                continue;
            
            // 精准检测：计算内容哈希
            var newHash = ComputeHash128(file.fullPath);
            if (cachedEntry.contentHash == newHash)
                continue;   // 仅元数据变化（如时间戳），内容未变
            
            // 真正变更的资源
            changedAssets.Add(file.guid);
        }
        
        // Phase 2: 传播依赖变更
        var transitiveChanged = new HashSet<string>(changedAssets);
        var queue = new Queue<string>(changedAssets);
        
        while (queue.Count > 0)
        {
            var changed = queue.Dequeue();
            
            // 查找引用此文件的所有文件
            foreach (var dependent in GetDependents(changed))
            {
                if (transitiveChanged.Add(dependent))
                {
                    queue.Enqueue(dependent);
                }
            }
        }
        
        return transitiveChanged;
    }
}
```

**关键优化点**：
- 基于 `LastWriteTime` 做第一级过滤，避免对所有文件计算哈希
- 内容哈希确保即使修改后又还原，也不会触发重导入
- 依赖传播保证A引用的B发生变化时，A也会被重处理

### 2.2 依赖图与传播链

ADB v2 维护了一个完整的资源依赖图。理解这个图是优化增量构建的关键：

```
┌─────────────────────────────────────────────────┐
│               资源依赖链示例                      │
├─────────────────────────────────────────────────┤
│                                                   │
│  Material.shader ──> ShaderVariants ──> Shader    │
│       │                                           │
│       v                                           │
│  Material         ──> Texture.png                  │
│       │                                           │
│       v                                           │
│  Prefab.prefab    ──> Mesh.fbx                     │
│       │              ──> Animation.controller       │
│       v                                            │
│  Scene.unity      ──> Prefab (引用)                │
│                                                    │
└─────────────────────────────────────────────────┘
```

当 `Texture.png` 被修改时，传播链为：
1. `Texture.png` → 重导入 → 更新 artifact
2. `Material`（引用了纹理）→ 缓存无效 → 重构建材
3. `Prefab`（使用了材质）→ 缓存无效 → 重序列化
4. `Scene`（包含了Prefab实例）→ 缓存无效

**传播抑制策略**：
- 如果只是纹理内部压缩参数变化，Material不需要重导入，但需要重新build
- 如果只是修改了Scene中的Transform位置，所有引用路径需要重新序列化
- 使用 **Fast Import Mode** 可以跳过非关键变更的传播

#### 策略3：合理组织资源目录

目录结构直接影响变更传播范围：

```
❌ 差的做法：
Assets/
└── Resources/
    ├── UI/
    ├── Characters/
    ├── Scenes/
    └── Effects/

✅ 好的做法：
Assets/
├── _Game/
│   ├── UI/
│   ├── Characters/
│   │   ├── Textures/     # 只包含角色纹理
│   │   ├── Materials/    # 只包含角色材质
│   │   └── Prefabs/      # 只包含角色预制体
│   ├── Scenes/
│   └── Effects/
├── _ThirdParty/          # 第三方资源，很少变
└── _Editor/              # 编辑器工具，不影响运行时
```

**分层原则**：
- 按照**变更频率**组织资源目录
- 高频变更的资源放在小粒度目录中，降低传播范围
- 低频变动的第三方库单独分区，利用缓存长期复用

## 三、Scriptable Build Pipeline：增量打包的实战

Scriptable Build Pipeline（SBP）是 Unity 2019.3 引入的下一代构建管线，替代了传统的 `BuildPipeline.BuildAssetBundles`。

### 3.1 SBP 的核心概念

SBP 将构建过程拆解为一系列可编程的 **Build Task**：

```csharp
using UnityEditor.Build.Pipeline;
using UnityEditor.Build.Pipeline.Interfaces;
using UnityEditor.Build.Pipeline.Tasks;

public class CustomBuildPipeline
{
    // SBP 内置的构建任务链
    public static IList<IBuildTask> CreateTaskList()
    {
        return new List<IBuildTask>
        {
            // 1. 前置检查
            new PrefabPackingTask(),
            new SpritePackingTask(),
            
            // 2. 资源计算
            new CalculateAssetDependencyData(),
            new GenerateBundleCommands(),
            
            // 3. 打包
            new BuildBundlesTask(),
            new GenerateBundlePacking(),
            
            // 4. 后处理
            new GenerateLinkXml(),
            new PostPackingCallback(),
            new AppendBundleHash()
        };
    }
}
```

每个Task都可以独立判断是否需要执行，这是增量构建的理论基础。

### 3.2 增量构建缓存机制

SBP 的增量构建依赖 **Build Cache**：

```csharp
// SBP 增量缓存的核心逻辑
public class SBPCacheSystem
{
    // 缓存条目
    class CacheEntry
    {
        public string guid;           // 资源GUID
        public Hash128 hash;          // 当前内容的哈希
        public Hash128[] dependencies; // 依赖资源哈希
        public string cachedPath;     // 缓存产物路径
        public long fileSize;         // 产物大小
    }

    public bool TryGetCachedBuild(
        IBundleBuildParameters parameters,
        IBundleBuildContent content,
        out IBundleBuildResults results)
    {
        results = null;
        
        // 1. 计算当前构建上下文哈希
        var contextHash = ComputeContextHash(parameters, content);
        
        // 2. 查找缓存
        var cacheKey = BuildCacheKey(contextHash);
        var cachedData = LoadFromCache(cacheKey);
        
        if (cachedData == null)
            return false;  // 缓存未命中
        
        // 3. 验证缓存有效性
        foreach (var entry in cachedData.Entries)
        {
            var currentHash = ComputeAssetHash(entry.guid);
            if (currentHash != entry.hash)
                return false;  // 资源已变更，缓存失效
                
            // 检查依赖是否变更
            foreach (var depHash in entry.dependencies)
            {
                if (!ValidateDependency(depHash))
                    return false;
            }
        }
        
        // 4. 命中缓存，重映射输出路径
        results = cachedData.ToBuildResults();
        return true;
    }

    // 构建上下文哈希：参数 + 所有资源GUID列表
    private Hash128 ComputeContextHash(
        IBundleBuildParameters parameters,
        IBundleBuildContent content)
    {
        using (var stream = new MemoryStream())
        using (var writer = new BinaryWriter(stream))
        {
            // 构建参数
            writer.Write(parameters.ContiguousBundles ? 1 : 0);
            writer.Write(parameters.DisableWriteTypeTree ? 1 : 0);
            
            // 所有资源的GUID列表（排序后）
            var sortedAssets = content.AssetBundleBuild
                .SelectMany(b => b.addressableNames)
                .OrderBy(n => n)
                .ToList();
                
            foreach (var asset in sortedAssets)
                writer.Write(asset);
            
            writer.Flush();
            return Hash128.Compute(stream.ToArray());
        }
    }
}
```

## 四、CI/CD 缓存策略：让构建速度翻倍

在 CI 环境中，增量构建面临特殊挑战——每次构建都是"冷启动"（全新的工作目录）。缓存策略因此成为 CI 构建加速的核心。

### 4.1 缓存什么

| 缓存目标 | 路径 | 大小 | 命中率 | 重要性 |
|---------|------|------|--------|--------|
| Library 目录 | `Library/` | 2-8GB | 80-95% | ⭐⭐⭐⭐⭐ |
| SBP 缓存 | `Library/BuildCache/` | 1-3GB | 70-90% | ⭐⭐⭐⭐⭐ |
| 包缓存 | `Library/PackageCache/` | 500MB-2GB | 95%+ | ⭐⭐⭐⭐ |
| IL2CPP 缓存 | `Library/il2cpp_cache/` | 200MB-1GB | 60-80% | ⭐⭐⭐ |
| 脚本缓存 | `Library/ScriptAssemblies/` | 50-200MB | 70-85% | ⭐⭐⭐ |

### 4.2 GitHub Actions 缓存配置

```yaml
# .github/workflows/unity-build.yml
name: Unity Incremental Build

on:
  push:
    branches: [main, develop, release/*]
  pull_request:
    branches: [main]

env:
  UNITY_VERSION: 2022.3.20f1
  PROJECT_PATH: .

jobs:
  build-android:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true
          fetch-depth: 0  # 获取完整git历史，用于变更检测

      # 关键：Library 缓存 —— 增量构建的基础
      - name: Cache Unity Library
        id: cache-library
        uses: actions/cache@v3
        with:
          path: |
            Library/
            !Library/BuildCache/**
          key: library-${{ runner.os }}-${{ env.UNITY_VERSION }}-$
            {{ hashFiles('Assets/**', 'Packages/**', 'ProjectSettings/**') }}
          restore-keys: |
            library-${{ runner.os }}-${{ env.UNITY_VERSION }}-
            library-${{ runner.os }}-

      # SBP 构建缓存
      - name: Cache SBP Build Cache
        id: cache-sbp
        uses: actions/cache@v3
        with:
          path: Library/BuildCache/
          key: sbp-${{ runner.os }}-$
            {{ hashFiles('Assets/Resources/**', 'Assets/Scenes/**') }}
          restore-keys: |
            sbp-${{ runner.os }}-

      # IL2CPP 缓存
      - name: Cache IL2CPP

          path: Library/il2cpp_cache/

        uses: actions/cache@v3

      - name: Upload Build Log

        uses: actions/upload-artifact@v3
        with:
          name: build-log
          path: build.log
          retention-days: 3

      - name: Upload Artifact
        uses: actions/upload-artifact@v3
        with:
          name: android-build
          path: Builds/Android/
          retention-days: 7
```

### 4.4 缓存密钥设计策略

缓存命中率的关键在于 **key 的粒度选择**：

```yaml
# 策略1: 精确匹配（最高命中率，但缓存膨胀快）
key: library-${{ hashFiles('Assets/**') }}
# 优点：只要文件没变就一定命中
# 缺点：任何文件变化都会miss，缓存数量暴增

# 策略2: 分支级缓存（推荐）
key: library-${{ runner.os }}-${{ github.ref_name }}-$
  {{ hashFiles('Assets/Resources/**') }}
restore-keys: |
  library-${{ runner.os }}-${{ github.ref_name }}-
  library-${{ runner.os }}-develop-
  library-${{ runner.os }}-
# 优点：分支内高命中率，分支切换时从develop回溯
# 缺点：跨分支切换时初始miss

# 策略3: 时间窗口（适用于频繁提交的分支）
key: library-${{ runner.os }}-$
  {{ steps.date.outputs.week-of-year }}
# 优点：缓存数量可控，一周内高效
# 缺点：整周只有一份，换分支会清空
```

**推荐方案**：混合策略
- Primary key 使用 `分支名 + 资源目录哈希`
- Restore keys 使用 `分支名` → `develop` → `空` 的降级链
- 设置缓存大小上限（如 8GB），避免缓存膨胀

### 4.5 缓存预热与分布式缓存

对于大型团队，建议部署 **分布式缓存加速**：

```bash
# 使用 Nexus/Artifactory 作为缓存后端
# 构建脚本：推送缓存到中央仓库

function upload_cache() {
  local cache_path="Library"
  local cache_key="unity-${CI_COMMIT_REF_SLUG}-$(date +%Y%m%d)"
  
  tar czf /tmp/cache.tar.gz \
    -C $(dirname $cache_path) $(basename $cache_path)
  
  curl -u $NEXUS_CREDS --upload-file /tmp/cache.tar.gz \
    "${NEXUS_URL}/repository/unity-cache/${cache_key}.tar.gz"
}

function download_cache() {
  local cache_key="unity-${CI_COMMIT_REF_SLUG}"
  
  # 尝试分支级缓存
  if curl -f -o /tmp/cache.tar.gz \
    "${NEXUS_URL}/repository/unity-cache/${cache_key}.tar.gz"; then
    tar xzf /tmp/cache.tar.gz -C / || true
    echo "下载缓存成功：${cache_key}"
  else
    echo "缓存未命中，执行全量构建"
  fi
}

# 在 Pipeline 中
before_script:
  - download_cache

after_script:
  - upload_cache
```

## 五、构建耗时分析与优化实战

没有测量就没有优化。构建时间的精细量化是加速的前提。

### 5.1 构建计时系统

```csharp
using System;
using System.Collections.Generic;
using System.Diagnostics;
using System.IO;
using UnityEditor;
using UnityEditor.Build.Reporting;
using UnityEngine;

/// <summary>
/// 构建计时与分析系统
/// </summary>
public static class BuildTimer
{
    private static readonly Dictionary<string, Stopwatch> _timers = new();
    private static readonly List<BuildTiming> _records = new();
    
    public struct BuildTiming
    {
        public string phase;
        public long elapsedMs;
        public long memoryMB;
        public DateTime timestamp;
    }

    [InitializeOnLoadMethod]
    private static void Subscribe()
    {
        // 订阅构建事件
        BuildEvents.buildStarted += OnBuildStarted;
        BuildEvents.buildCompleted += OnBuildCompleted;
    }

    private static void OnBuildStarted()
    {
        _timers.Clear();
        _records.Clear();
        StartPhase("Total");
        
        // 记录初始状态
        var logPath = $"BuildLogs/build_{DateTime.Now:yyyyMMdd_HHmmss}.log";
        Directory.CreateDirectory("BuildLogs");
        File.WriteAllText(logPath, "Build Start\n");
    }

    public static void StartPhase(string phaseName)
    {
        if (_timers.TryGetValue(phaseName, out var existing))
        {
            existing.Restart();
        }
        else
        {
            var sw = new Stopwatch();
            sw.Start();
            _timers[phaseName] = sw;
        }
    }

    public static void EndPhase(string phaseName)
    {
        if (!_timers.TryGetValue(phaseName, out var sw)) return;
        
        sw.Stop();
        var memory = GC.GetTotalMemory(false) / (1024 * 1024);
        
        _records.Add(new BuildTiming
        {
            phase = phaseName,
            elapsedMs = sw.ElapsedMilliseconds,
            memoryMB = memory,
            timestamp = DateTime.Now
        });
        
        Debug.Log($"[BuildTimer] Phase '{phaseName}' 耗时: {sw.Elapsed.TotalSeconds:F2}s, " +
                  $"内存: {memory}MB");
    }

    private static void OnBuildCompleted(BuildReport report)
    {
        EndPhase("Total");
        ExportTimingReport();
    }

    private static void ExportTimingReport()
    {
        var reportPath = $"BuildLogs/timing_{DateTime.Now:yyyyMMdd_HHmmss}.csv";
        
        using (var writer = new StreamWriter(reportPath))
        {
            writer.WriteLine("Phase,Elapsed(s),Memory(MB),Timestamp");
            
            foreach (var record in _records)
            {
                writer.WriteLine(
                    $"{record.phase}," +
                    $"{record.elapsedMs / 1000.0:F2}," +
                    $"{record.memoryMB}," +
                    $"{record.timestamp:HH:mm:ss}");
            }
        }
        
        Debug.Log($"[BuildTimer] 构建耗时报告已导出: {reportPath}");
    }
}
```

```csharp
public static class IncrementalBuildScript
{
    public static void IncrementalBuild()
    {
        var stopwatch = Stopwatch.StartNew();
        
        // Phase 1: Domain Reload
        BuildTimer.StartPhase("DomainReload");
        bool needReload = CheckScriptChanges();
        if (needReload)
        {
            // 脚本有变更，需要完整重载
            EditorApplication.UnlockReloadAssemblies();
        }
        BuildTimer.EndPhase("DomainReload");
        
        // Phase 2: Import
        BuildTimer.StartPhase("AssetImport");
        var changes = AssetDatabase.Refresh(ImportAssetOptions.ForceUnloadAssets);
        BuildTimer.EndPhase("AssetImport");
        
        // Phase 3: Build
        BuildTimer.StartPhase("BuildPlayer");
        var options = new BuildPlayerOptions
        {
            scenes = GetScenes(),
            locationPathName = "Builds/Android/game.apk",
            target = BuildTarget.Android,
            options = BuildOptions.None
        };
        
        var report = BuildPipeline.BuildPlayer(options);
        BuildTimer.EndPhase("BuildPlayer");
        
        stopwatch.Stop();
        
        // 打印增量构建明细
        var result = report.summary;
        Debug.Log($"[IncrementalBuild] ===== 构建报告 =====");
        Debug.Log($"总耗时: {stopwatch.Elapsed.TotalSeconds:F1}s");
        Debug.Log($"构建结果: {result.result}");
        Debug.Log($"包体大小: {result.totalSize / 1024 / 1024:F1}MB");
        Debug.Log($"是否有增量构建: {result.totalSize > 0}");
        
        // 输出构建时是否使用了缓存
        if (File.Exists("Library/BuildCache/cache_stats.json"))
        {
            var stats = File.ReadAllText("Library/BuildCache/cache_stats.json");
            Debug.Log($"[IncrementalBuild] 缓存统计: {stats}");
        }
    }

    private static bool CheckScriptChanges()
    {
        // 通过git diff检测脚本变更
        var psi = new ProcessStartInfo
        {
            FileName = "git",
            Arguments = "diff --name-only HEAD~1 -- '*.cs'",
            RedirectStandardOutput = true,
            UseShellExecute = false
        };
        
        using var process = Process.Start(psi);
        string output = process.StandardOutput.ReadToEnd();
        process.WaitForExit();
        
        return !string.IsNullOrWhiteSpace(output);
    }

    private static string[] GetScenes()
    {
        var scenes = new List<string>();
        foreach (var scene in EditorBuildSettings.scenes)
            if (scene.enabled) scenes.Add(scene.path);
        return scenes.ToArray();
    }
}
```

```csharp
// 构建诊断工具
public static class BuildDiagnostics
{
    public static void Diagnose()
    {
        // 1. 检查资源依赖深度
        var deepAssets = AssetDatabase.FindAssets("t:Object")
            .Select(AssetDatabase.GUIDToAssetPath)
            .Where(p => p.StartsWith("Assets/"))
            .Select(p => new {
                path = p,
                depCount = AssetDatabase.GetDependencies(p, true).Length
            })
            .OrderByDescending(x => x.depCount)
            .Take(20);

        Debug.Log("=== 依赖最多的资源 Top 20 ===");
        foreach (var asset in deepAssets)
        {
            Debug.Log($"{asset.path}: {asset.depCount} 个依赖");
        }
        
        // 2. 检查大文件
        var largeAssets = Directory.GetFiles("Assets", "*.*", SearchOption.AllDirectories)
            .Select(f => new FileInfo(f))
            .Where(f => f.Length > 50 * 1024 * 1024) // >50MB
            .OrderByDescending(f => f.Length);
            
        Debug.Log("=== 超过50MB的大型资源 ===");
        foreach (var file in largeAssets)
        {
            Debug.Log($"{file.FullName}: {file.Length / 1024 / 1024:F1}MB");
        }
        
        // 3. 检查Texture压缩状态
        var uncompressedTextures = AssetDatabase.FindAssets("t:Texture2D")
            .Select(AssetDatabase.GUIDToAssetPath)
            .Where(p => p.StartsWith("Assets/"))
            .Select(TryGetTextureInfo)
            .Where(t => t != null && !t.IsCompressed)
            .Take(20);
            
        Debug.Log("=== 未压缩的纹理 ===");
        foreach (var tex in uncompressedTextures)
        {
            Debug.Log($"{tex.Path}: {tex.Width}x{tex.Height} {tex.Format}");
        }
    }

    private static TextureInfo TryGetTextureInfo(string assetPath)
    {
        var importer = AssetImporter.GetAtPath(assetPath) as TextureImporter;
        if (importer == null) return null;
        
        return new TextureInfo
        {
            Path = assetPath,
            IsCompressed = importer.textureCompression != TextureImporterCompression.Uncompressed,
            Width = 0,
            Height = 0,
            Format = importer.textureFormat.ToString()
        };
    }

    class TextureInfo
    {
        public string Path;
        public bool IsCompressed;
        public int Width;
        public int Height;
        public string Format;
    }
```

### 6.2 推荐配置基线

根据项目规模给出推荐配置：

| 项目类型 | Library缓存 | Cache Server | SBP | CI缓存 | 分布式缓存 |
|----------|------------|-------------|-----|--------|-----------|
| 小团队（<10人） | ✅ | ✅(局域网) | ✅ | ❌ | ❌ |
| 中团队（10-50人） | ✅ | ✅(专用服务器) | ✅ | ✅(GitHub Actions) | ❌ |
| 大团队（50-200人） | ✅ | ✅(集群) | ✅(自定义Task) | ✅(自定义Key策略) | ✅(Nexus) |
| 超大型（200+人） | ✅ | ✅(多区域CDN) | ✅(自定义Task) | ✅(预热+回滚) | ✅(S3/MinIO) |

### 6.3 关键决策点

1. **SBP vs 传统API**：新项目一律使用 SBP；旧项目迁移时可先保持双管线运行，逐步切换
2. **缓存粒度**：宁可缓存范围大一些（包括Library），也不因缓存过期导致全量构建
3. **Cache Server vs CI缓存**：两者互补——Cache Server解决开发机之间的导入缓存共享，CI缓存解决流水线的冷启动问题
4. **IL2CPP缓存**：在代码频繁变更的阶段，IL2CPP缓存失效频繁，可考虑临时切换到Mono进行开发构建

### 6.4 注意事项

- **缓存安全问题**：Library 目录中包含了编译后的中间文件，不同Unity版本之间的Library 缓存不兼容
- **缓存膨胀问题**：长期运行的CI缓存可能膨胀到10GB+，需设置大小上限和清理策略
- **缓存一致性**：如果团队中有人更新了Unity版本或Package版本，所有缓存将失效，需手动清除
- **CI缓存过期**：GitHub Actions缓存7天无访问即过期，对低频分支需考虑缓存预热
